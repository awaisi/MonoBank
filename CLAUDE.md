# MonoBank — repository guide

MonoBank is a mobile-first shared banking companion for a classic property-trading board game. Players open a game, share its URL, and move money, manage deeds, collect rent, trade, mortgage, and build from any device. It is an unofficial fan-made companion.

- You **may** name Monopoly descriptively (nominative use): "unofficial Monopoly® banker", "for Monopoly game night". Use ® on the first prominent mention in a view.

- **Never** use Hasbro's logos, artwork, fonts, mascots, box or board imagery, trademarked edition names, or wording that implies an official or endorsed product. Never put "Monopoly" in the product name; it stays **MonoBank**.

## Commands

```bash
npm test          # node --test (test/*.test.mjs)
npm run coverage  # tests + coverage report (node --experimental-test-coverage)
npm run coverage:check  # fails below 100% line coverage on the core modules (run in CI)
npm run check     # node --check on server.mjs, lib/*.mjs, public/app.js, public/qr.js, public/admin.js
npm run e2e       # Playwright browser test (e2e/ui.e2e.mjs); needs Playwright installed, skips otherwise
npm run dev       # node --watch server.mjs → http://localhost:3000
docker build -t monobank . && docker run -p 3000:3000 monobank
```

Requires Node.js 22+. There are **no runtime or dev dependencies**; keep it that way. Do not add a framework, bundler, or npm package without explicit approval. Use `node:test` / `node:assert` for tests.

Run `npm run check && npm test` before every commit, and `npm run e2e` for any UI change. If a new `.js`/`.mjs` source file is added, add it to the `check` script.

### Game model rules

- **The server is the source of truth.** Every rule is enforced in `lib/game.mjs`; the client only mirrors rules for display (button labels, hidden controls). Never rely on client-side validation.
- **One action type per change.** New behavior goes through `performAction` → `applyAction` with a new `case`, validates input with `GameError` messages written for players, and calls `record()` (or `move()`) exactly once per action so `revision` increments once and undo has one ledger entry to mark.
- **Actions are atomic and undoable.** `performAction` snapshots `UNDOABLE_KEYS` (`players`, `deeds`, `freeParking`, `status`, `endedAt`, `winnerIds`, `playedUntil`) before each action, restores it if the action throws, and pushes it onto `game.history` (last 50) on success. Any new mutable game state **must be added to `UNDOABLE_KEYS`**, or undo will not restore it. `undo` marks the original entry `undone: true` and records a new entry; transactions and `revision` never roll back. `publicGame()` strips `history` and exposes only `undo: { label, transactionId }`.
- **Bankruptcy and game end.** Bankrupt players (`player.bankrupt`) are rejected by `player()` for every action and hidden from client pickers. `end-game` can run at any time: without `winnerId` the highest net worth wins (ties share `winnerIds`); with `winnerId` that player wins (validated through `player()`, so not bankrupt) and the ledger detail says the table chose. **Play time** is not creation-to-Finish: `record()` sets `game.startedAt` once on the first entry that isn't `system`/`end`/`undo` (`NOT_PLAY`; deliberately not undoable, like `createdAt`), and `end-game` sets `playedUntil` to the newest such entry before Finish (undoable). `playTime(game)` (in `publicGame` and the spectator view) returns `{ startedAt, endedAt, minutes }` once ended; older saves fall back to the oldest move in the ledger. `status: 'ended'` blocks every action except `undo`. Net worth (`netWorth()`, `standings()`) is equity: cash + deeds at list price (mortgaged deeds at list price minus `unmortgageCost()`) + buildings at resale value (half cost). Keep it consistent so reversible moves net to zero. `netWorth().raisable` = building resale + mortgage value of unmortgaged deeds.
- **Ledger.** `game.transactions` (newest first) keeps up to `TRANSACTION_LIMIT` (2,000) entries; `record()` trims past that and counts the overflow in `game.transactionsDropped`. After every successful action and every undo, `stampBalances()` adds `balances` and `deltas` (one number per seat, in `game.players` order) to the new entry; the Activity page and `activityStats()` rely on them (older entries without stamps fall back to `fromId`/`toId`/`amount`). `publicGame()` sends only the newest `LEDGER_WINDOW` (150) entries plus `transactionCount`, `transactionsDropped` and `activity` (computed over the whole stored ledger, skipping undone entries and `system`/`end`/`undo`). Older pages come from `ledgerPage()` via `GET …/transactions?before=`; `ledgerCsv()` serves `GET …/activity.csv` (escape formula-like cells). Both also exist read-only under `/api/watch/:token/`. Anything that needs whole-game totals must use `activity` (server), never the client's partial list.
- **Money is whole dollars.** Use the `money()` helper for any amount from input.
- **Balances never go negative.** Every debit calls `assertCanPay(game, payer, amount)` **before** changing anything: `move()` (transfers, taxes, Free Parking, rent), `buy`, `unmortgage`, building `buy`, and the net cash side of a `trade`. It throws a `GameError` with `code: 'insufficient-funds'` and `details: { playerId, needed, balance, shortfall, raisable }`; the server returns `code`/`details` in the JSON body and the client opens the Raise cash dialog. Any new action that takes money from a player must call it. Older saved games may hold negative balances; don't assume `balance >= 0` when reading.
- **Optimistic concurrency.** Clients send `expectedRevision`; a mismatch returns HTTP 409 and the client reloads. Keep this for every action.
- **Players:** 2–8 per game (`MIN_PLAYERS`/`MAX_PLAYERS` in `lib/game.mjs`), each with a seat color and a generic token name (no official playing-piece names). `public/app.js` mirrors `MAX_PLAYERS` and the colors as `PLAYER_COLORS` for the setup form; a test fails if they drift. Layouts must work with 8 players: the player tiles scroll sideways (`.players-bar.crowded` makes them narrower), and the identity picker becomes the two-column `.identity-options.many`.
- **Accounts** are player IDs plus the special IDs `bank` and `parking` (Free Parking pot, only when that house rule is on).
- **House rules** live in `game.rules` (defaults in `DEFAULT_RULES`: Free Parking jackpot + seed, $400 on GO, no rent in jail, auctions, even building, mortgage interest %, `showAllBalances`), are normalized by `normalizeRules()` at creation, and are fixed for the life of a game. The pot balance is `game.freeParking`; jail status is `player.inJail`. The client's `rulesSummary()` in `public/app.js` mirrors the server's for display only. Add a new rule by: default in `DEFAULT_RULES`, validation in `normalizeRules()`, enforcement in `performAction`/`calculateRent`, a setup control in `index.html` + `app.js`, the rules summary in `rulesSummary()`, tests, and the README "House rules" table.
- **Persistence.** The server must call `await store.save(game)` after every successful action (and `store.create` saves new games). The whole game object, including `history`, is persisted, so anything added to the game is saved automatically — keep it JSON-serializable. Persistence failures are logged, never thrown. `store.get()` is async and loads from disk on a cache miss. Game files are only ever written by `GameStore`; don't read or write `DATA_DIR` elsewhere.
- **Live updates.** After every successful action the server calls `streams.publish(game)` (after `store.save`). Each subscriber gets its own view: `publicGame` for players, `spectatorView` for spectators. Never publish on a failed action. Open streams must not block shutdown: `server.close()` ends them first.
- **Spectators.** A game has two secrets: `id` (full control) and `viewToken` (read-only). `spectatorView()` must never contain `id` (tests assert the ID appears nowhere in spectator payloads or pages), and there must be no write route under `/api/watch/`. Any new field that could reveal `id` must be stripped there. While `balancesHidden(game)` (game running and `rules.showAllBalances === false`; legacy games without the key stay open), `spectatorView()` nulls each player's `balance` and the standings' `cash`/`total`/`raisable`/`rank` and drops per-entry `balances`; the watch routes use `spectatorLedgerPage()` and `ledgerCsv(game, { hideBalances })`. Any new field that reveals a player's cash or net worth must be stripped there too.
- **Retention and memory.** `GameStore.isExpired()` uses `ttlMs` (30 days) for active games and `endedTtlMs` (7 days, capped by `ttlMs`) for ended ones; on-disk files not in memory are judged by file age against `ttlMs`. `sweep()` (every 15 min) also unloads games idle for `idleUnloadMs` (2 h) without pending writes; they load again from disk on the next request. `save()` re-adopts a game object whose revision is newer than the in-memory copy, so a request that held a game across an unload can't be overwritten by a stale reload. Update the home page fine print and README if retention changes.
- **Admin page.** `/admin` (and `/admin.html`, `/admin.js`) plus `GET /api/admin/stats` exist only when `createAppServer({ adminToken })` gets a token of at least `MIN_ADMIN_TOKEN_LENGTH` (24) characters; production reads `ADMIN_TOKEN` via `adminTokenFromEnv()`. The API takes the token only as `Authorization: Bearer` (never a query string), compares it in constant time, and limits wrong tokens to 10 per 15 minutes per address (401 with `WWW-Authenticate: Bearer`). Admin pages send `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store`, carry a `noindex` meta tag, and must never be linked from public pages, added to the sitemap, or listed in `robots.txt`. Stats come from `store.usage(summarizeGame)` (each file summarized once, re-read only when its mtime changes) and `RuntimeMetrics` (requests, errors by code, actions, live connections, save timings; reset on restart). **Never put game IDs, view tokens or player names in admin output** (tests assert this); notes appear only when typed 3+ times.
- **Single instance.** Memory is the working copy, so the app must run as exactly one replica. Do not scale out without moving to a shared database with concurrency control.
- **Abuse limits** (`server.mjs`): every `/api/` request counts against the per-IP API limit, and `POST /api/games` also counts against the creation limit. Limit errors are `GameError`s with status 429 and a `Retry-After` header. `X-Forwarded-For` is honoured only with `TRUST_PROXY=1`.

### Client conventions

- Escape every player-provided string with `escapeHtml()` before putting it in `innerHTML`.
- **Caching:** the server sends `Cache-Control: no-cache` + `ETag` for every static file, so deploys take effect immediately. Never reintroduce `max-age` on HTML, CSS or JS. `index.html` references `styles.css?v=N` and `app.js?v=N`; bump `N` only if browsers might still hold assets from an old long-cache policy.
- **Compression.** `server.mjs` compresses static files with brotli (or gzip), cached per file version with an encoding-specific ETag (`"<hash>-br"`), and JSON/CSV responses with gzip; `GameStreams.open()` gzips the event stream with `Z_SYNC_FLUSH` so every event goes out immediately. Bodies under 1 KB and images are sent as is. Always send `Vary: Accept-Encoding`. Security headers include HSTS.
- The CSP in `server.mjs` (`script-src 'self'`, `style-src 'self'`) blocks inline scripts **and `style="…"` attributes in HTML strings**. For per-element values (player/deed colors), put `data-vars="--name=value;--other=value"` in the markup and call `applyStyleVars(container)` after setting `innerHTML`; it applies them through the CSSOM. Keep all other styling in `styles.css`. Check the browser console for CSP errors after UI changes.
- Keep the 320 px mobile layout, keyboard focus, labels, and `aria-live` toasts working. Respect `prefers-reduced-motion`.
- Verify UI changes in a real browser (Playwright is available in cloud sessions): create a game, exercise the changed flow, and confirm no console errors and no horizontal scroll at 375 px.
- `styles.css` is compact (one block per line); append new rules in the same style, and delete rules that a change makes unused.
- **Layout:** the sticky `.topbar` is the only header on every page (it adds `env(safe-area-inset-top)` because the viewport uses `viewport-fit=cover`) and stays minimal: brand on the left; on a game, `#game-actions` adds the live `.game-chip` (`#session-code`, or `VIEW` for spectators), the gold **Invite** button (`#show-qr`, players/spectators toggle), and the **⋯** overflow menu (`#menu-button` → `#game-menu`, `role="menu"`) holding Copy game link, Copy spectator link, Switch player…, Download activity (CSV) (`#export-activity`, a link), Sound & vibration (`menuitemcheckbox`), and Finish game… (`#end-game`, opens `#end-dialog` to pick a winner). New game-wide actions go **in the menu**, not as new header buttons. `setMenu()` handles open/close; the menu closes on item click, outside click, and Escape, and supports arrow keys.
- **Live client state.** All incoming state goes through `applyLatest()` (polling and the `EventSource`), which ignores anything not newer than the current `revision` and suppresses the remote chime while this device's own action is in flight (`acting`). Polling runs every 3.5 s while the stream is down and every 30 s as a safety net while it's live; `.game-chip.polling` shows the amber dot.
- **This phone is me.** The device's choice lives in `localStorage` under `monobank:me:<gameId>` (`me` = player ID or `'banker'`). It only changes the view (me-bar, first `.is-me` tile with the You badge, pre-filled selects); it never restricts what the device can do, and the server knows nothing about it.
- **Spectator mode** (`/watch/<token>`): `body.spectator` hides every write control via CSS, `submitAction()` refuses to send, `switchView()` keeps spectators on Deeds/Activity, and the deed dialog shows "View only". Mark menu items that make no sense for spectators with `.player-only`.
- **Player order:** use `orderedPlayers()` (this device's player first, then seat order) for every list shown to the user (player tiles, `optionList()`, rent payers, activity filter). Use `seatOf(player)` for the seat token/color, never the list index.
- **One row of player tiles, no duplicate player lists.** `#players-bar` (full-bleed via `--gutter`, horizontal scroll with snap) is the only on-screen list of players; don't add player cards, strips or pill rows elsewhere. It is **not sticky**: a pinned, translucent bar showed content through it and glitched while scrolling on phones. Each `.player-tile` has the same structure on every tab, so the row keeps its height: `.tile-head` (token, `.tile-name`, `.you-badge`), `.tile-balance`, `.tile-meta` (net worth, deed count) and an optional `.tile-status` (jail, bankrupt, winner). `renderPlayersBar()` runs from `switchView()` (so on every render and tab change) and restores the row's `scrollLeft` after replacing its HTML. Outside Deeds, tiles are `[data-player]` buttons that open the player sheet, plus a `[data-parking]` tile when the jackpot rule is on. On Deeds the bar gets `.filtering` and becomes the owner filter: All deeds, players, and Bank, as `[data-owner]` buttons with `aria-pressed`, setting `deedOwnerFilter` (`'all'`, a player ID or `'bank'`; resets to `'all'` if that player leaves), ANDed with search and the status select.
- **Deeds tab modes:** `[data-deed-mode]` toggles **List** (search, status filter, `#deed-grid`) and **Sets** (`#deed-sets`, `renderSets()`); `renderDeeds()` picks the mode, and the choice is per device in `localStorage` (`monobank:deedMode`). Sets rows follow `SET_ORDER`; `setStatus()` (display only) labels a group complete / "needs 1" / split / unowned, or railroad counts. `deedOwnerFilter` dims non-matching tiles in Sets (`.set-tile.dim`) instead of hiding them. Keep the Sets view an abstract grid in MonoBank's style: don't turn it into a drawing of the game board (trade dress).
- **Player sheet:** `openSheet({ kind: 'player', id } | { kind: 'parking' })` renders into `#player-dialog`. `refreshSheet()` re-renders it on every `renderGame()`. Per-player things (net worth breakdown, deeds, quick actions, jail toggle, Free Parking payout, "This is me", Pay from) belong in the sheet, not in new on-page cards. Sheet actions use `[data-sheet]`. Quick actions (`quickActions()` list, `[data-quick]` buttons, `#quick-custom` form) go through `quickPay()` as plain `transfer` actions with a note and category: Bank → player for income; player → Bank, or → `parking` for taxes/fees when the jackpot rule is on. Keep them client-only shortcuts; a new kind of money movement still needs a server action.
- **Compact game head:** `.game-head` holds the title, rules line and me-bar. On phones the title is visually hidden and the rules line and me-bar share one row; view kickers and seals are hidden. Keep phone chrome above the console to a minimum.
- **Activity page:** `renderLedger()` merges each new window into `ledgerCache` (`mergeLedger()`: everything this device has seen, so entries that slide out of the window aren't lost) and filters by player (`#ledger-filter`), type (`#ledger-type` select, groups in `LEDGER_TYPES`) and search (`#ledger-search`). The controls live in one `.ledger-toolbar` row: on phones the search box shows only while `.searching` (toggled by `#ledger-search-toggle`, or while it holds text), a `[data-undo]` icon replaces the hidden view heading, and wide screens always show the search box and hide the toggle and icon. Keep the space above the list small on phones. Undone entries and undo entries are hidden unless `ledgerShowUndone`. It shows `ledgerLimit` rows (steps of 50) in 15-minute `.ledger-group` blocks; `loadEarlier()` raises the limit and fetches older pages. With a player selected, rows show signed `cashChange()` and the balance after. `renderActivitySummary()` writes a collapsible one-line `<details>` (title + teaser; open state kept in `summaryOpen` across re-renders) to `#ledger-summary` and the full card to `#side-summary`; `switchView()` sets `.desktop-grid.ledger-open` so wide screens show the summary in the sidebar instead of the mini list. `resetLedger()` runs in `showGame()`. The ⋯ menu's `#export-activity` link and the results screen point at `apiBase()/activity.csv`.
- **Network errors.** `api()` turns a failed `fetch` into `code: 'offline'` (nothing was sent) or `code: 'network'` (no answer) with plain-language messages, and 5xx responses into "MonoBank is having trouble". `submitAction()` reloads the game after a `network` error and asks the player to check Activity before retrying (the revision check already prevents double moves).
- **Readable text.** No visible text below 10px (timestamps 11px); secondary text uses `var(--muted)` (`#56625c`), which meets WCAG AA (4.5:1) on paper and cream backgrounds; don't introduce lighter greys for text. Don't put `aria-live` on regions that re-render on every live update (it floods screen readers); toasts are the live region.
- **Private balances.** `balancesPrivate()` / `moneyVisible(player)` decide what a phone shows: with private balances, only the player this phone is set to (never a banker-only phone or a spectator) until the game ends. Every place that shows a player's cash, net worth, "can raise" or balance-after must check `moneyVisible()` and show `HIDDEN` (`••••`) otherwise: player tiles, player sheet, identity picker, Finish game dialog (no leader or amounts), Activity balance-after. Payments, deeds and buildings stay public. It's a display courtesy, not security (players share the game link).
- **Insufficient funds:** `submitAction()` routes `insufficient-funds` errors to `openRaiseCash()` instead of a toast. Its Sell/Mortgage buttons mirror the server's eligibility (even selling, no buildings in the color set before mortgaging) for display only.
- **Destructive actions** (like bankruptcy) live in a collapsed danger-zone card, show a plain-language preview of the outcome, name the affected player on the confirm button, and remind the user that Undo can reverse them.

## SEO

- `index.html` `<head>` carries the title (≤ 60 chars), meta description (120–170 chars, checked by tests), canonical `https://monobank.divviq.app/`, Open Graph and Twitter card tags pointing at `/og-image.jpg`, and a `WebApplication` JSON-LD block (a data block, so it is allowed by the CSP).
- Game and spectator pages are private sessions: the server sends `X-Robots-Tag: noindex, nofollow` for `/game/*` and `/watch/*` and `noindex` for API responses; `robots.txt` disallows `/game/` and `/api/`. `app.js` sets `document.title` to `Game XXXX · MonoBank` in a game and restores the home title on the setup screen.
- If the domain changes, update the canonical URL, `og:url`/`og:image`, JSON-LD `url`/`image`, `robots.txt` and `sitemap.xml` together. Regenerate `og-image.jpg` (no Hasbro artwork) if the headline changes.

## Deployment

- Pull requests to `main` run the build job of `azure-deploy.yml` only (check, unit tests, `coverage:check`, Playwright e2e with `E2E_REQUIRED=1`, Docker build); it never deploys from a PR. Playwright (pinned version) is installed in `$RUNNER_TEMP` and found through `NODE_PATH`, so the repo keeps zero dependencies.
- Pushing to `main` runs `azure-deploy.yml`: check + test + coverage gate + e2e → provision shared infra → build/push image to ACR (tagged with the commit SHA) → deploy the container app → keep Cloudflare DNS and the managed certificate for `monobank.divviq.app` → verify `/health` on both URLs.
- Hosting is **Azure Container Apps** with exactly one always-on replica (`minReplicas = maxReplicas = 1`). The subscription has **no App Service quota**; do not reintroduce App Service.
- **Durable storage** is an Azure Files share (`games`) in storage account `mbst<suffix>`, registered on the environment as storage `games` (account key via Bicep `listKeys`) and mounted at `/data` with `uid=1000,gid=1000` so the `node` user can write. The app gets `DATA_DIR=/data` and `TRUST_PROXY=1`.
- The deploy creates a **persistence probe** game before rolling out and fails unless the new revision reports `storage: file` and the probe game still exists afterwards. Do not remove this check.
- Azure auth is OIDC (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`). The deploy identity has **Contributor only**: it cannot create role assignments, which is why ACR uses its admin user for pulls.
- The Cloudflare `monobank` CNAME must stay **DNS only**; Azure renews the managed certificate through it.
- `infra/bootstrap-azure.sh` / the bootstrap workflow are one-time setup and need the `BOOTSTRAP_*` secrets, which may have been deleted. Do not depend on them for routine deploys.
- **Backups:** `azure-backup.yml` (daily at 09:23 UTC and on demand) snapshots the `games` share with `az storage share-rm snapshot` and prunes snapshots older than `KEEP_DAYS` (14). It uses management-plane commands only, because the deploy identity is Contributor. `azure-restore.yml` (manual) lists snapshots or restores one game: it validates the inputs (16-hex game ID, a snapshot time, the typed `RESTORE`), snapshots the current state first, downloads the file from the snapshot, checks it is a valid game with that ID, bumps `updatedAt` (so retention doesn't delete it again), uploads it, recreates `watch-<viewToken>.json`, restarts the latest revision (memory may hold an older copy; `store.flush()` only awaits in-flight writes, so a restart doesn't overwrite the restored file) and checks `GET /api/games/:id`. Both jobs use `environment: production`, because the OIDC federated credential is issued for that environment, and mask game IDs and keys in logs. Keep both workflows in sync with the storage layout (`<id>.json`, `watch-<token>.json`) if it changes.
- **Admin token:** the optional `ADMIN_TOKEN` GitHub secret reaches the deploy step's `env` from `secrets.*` (masked), goes to Bicep as the `@secure()` `adminToken` parameter, and becomes the Container Apps secret `admin-token` referenced by the `ADMIN_TOKEN` env var. Empty means no secret and no admin page.
- Never commit secrets. Never put secrets in Bicep parameters files, hard-coded workflow `env`, or logs; secrets come only from GitHub `secrets.*`.

## Testing standard

- Every action needs tests for the success path, **each** `GameError` path, undo of the action, and at least one API-level test in `test/server.test.mjs` when it adds a new action type.
- Keep **100% line coverage** for `lib/game.mjs`, `lib/store.mjs`, `lib/rate-limit.mjs`, `lib/streams.mjs`, `lib/admin.mjs` and `public/qr.js` (`npm run coverage`). Do not lower coverage to land a feature. File-system error paths are tested by injecting `fs` into `GameStore`.
- CI enforces the coverage rule with `npm run coverage:check` and runs the browser tests; a pull request must be green before merging.
- UI changes: extend `e2e/ui.e2e.mjs` for the new flow and run `npm run e2e` (it also asserts no console/CSP errors and no horizontal scroll at 375 px; deliberate HTTP 400 rejections are the only console errors it ignores).

## Update all documents after every feature change (required)

A feature or behavior change is not done until, **in the same PR**:

1. **`README.md`**: highlights, the **"How to use" walkthrough** (keep it a short, current step-by-step game night: add, change or remove the step for any user-facing feature or renamed control, with the button names as they appear in the app), the relevant feature section, house rules table, API actions table, testing or deployment notes.
2. **`docs/FEATURE_PLAN.md`**: move the item to *Shipped* (with PR number), and add or reprioritize anything new that was discovered.
3. **`CLAUDE.md`** (this file): architecture table, game-model invariants, commands, conventions.
4. **In-app copy** in `public/index.html` (setup text, feature strip, help text) and any user-facing strings in `public/app.js`.
5. **Tests**: per the testing standard above.

Check each item explicitly before opening the PR, and list the docs you updated in the PR description.
